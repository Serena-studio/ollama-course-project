# 开发指令模板（完善版）· 进出口代理单证一致性智能体系统

> 使用说明：以下为补全后的完整指令，方括号【】内为我根据你的 FDE 演练产出填入的内容；技术栈部分按你"不许替换"的要求给出了默认选项，提交前请确认或改掉那一段即可，其余无需改动。

---

你是一名资深 AI 应用工程师，帮我开发一套进出口代理单证一致性智能体系统。请严格按我给出的技术栈和约束执行，不要自行替换框架、不要引入我没要求的中间件。

【项目背景】  
客户为上海外综服国际贸易有限公司（合成演练场景），业务链路五段：客户提供 → 单证检查 → 人工确认 → 委托作业 → 归档。现场痛点：发票、装箱单与订单的商品名称和单位不一致（f10）；客户更新装箱数量但商业发票版本未同步导致返工（f11，模拟异常）；现场习惯先群消息解决再补填表格，回填时间不等于发生时间（f13）；无统一关联编号（f30）。演练基线"每月 220 票、每票核对 42 分钟"为虚构样本，不得作为系统设计依据或收益测算。需求来源：业务发现报告六项结论，P0 三条为——缺项清单+来源定位（f15/f42）、版本有效期+确认状态双条件判定（f24）、异常存疑一律进人工队列（f44）。

【系统定位】  
本系统是"定位与提示"工具，不是审批或放行系统。核心交付物：一页缺项清单 + 对应来源位置（定位到原单据字段），供人工确认使用。智能体只承担：字段一致性比对、版本双条件判定、差异来源定位、人工队列分派提醒；不承担：审批、放行、覆盖原值、对外结论、自动申报归类或监管判断。验收口径：50 票样本预设差异全部定位到原单据字段（f02），每条结果关联来源与人工复核记录（f42）。

【用户与权限】

- 一线单证专员（对应林亦舟）：可发起查询、查看缺项清单、提交变更申请；不可确认放行。
- 业务负责人（对应顾明岚）：正式确认人，唯一可对结论签字确认的角色（f22：一线可提交变更，正式确认由业务负责人完成）。
- 审核与质量负责人（对应傅景）：人工队列出口，可暂停试点，查看全部审计记录（f44/f45）。
- 流程协调员（对应唐映秋）：维护交接清单与确认链，只读+登记权限。
- 系统角色（模型）：无审批权限，所有建议必须附带来源与人工复核入口（f14：系统建议不能覆盖原值或省略确认）。
- 所有一对一访问按授权范围控制，跨企业资料越权访问为零（f41）。

【技术栈，不许替换】

- 语言与运行时：Python 3.11+
- Web 框架：FastAPI（接口统一前缀 /api）
- 数据存储：SQLite（单文件，演示环境够用，不引入 MySQL/Redis/消息队列）
- 配置管理：PyYAML，全部配置集中在 config.yaml（含模型地址、密钥占位符、字段白名单、链路节点配置）
- LLM 接入：仅通过 OpenAI 兼容接口调用，模型名与地址从 config.yaml 读取（本次演练评分模型为 deepseek-flash，可配置替换）
- 前端：不做独立前端，FastAPI + Jinja2 模板渲染缺项清单页面即可
- 测试：pytest + httpx
- 不引入：Docker、Celery、MongoDB、ORM 框架（用 sqlite3 标准库）、任何云服务 SDK

【数据红线，硬约束】

1. 只读边界：系统只对接脱敏只读导出数据源，不实现任何写回、外部消息、执行类接口（f32）。
2. 人工队列：版本或关键字段无法确认时一律进入人工队列并暂停该票流程，禁止默认通过、禁止自动重试（f44、f35：不编造状态、不悄悄重试）。
3. 双时间戳：每次更新同时记录业务发生时间与系统接收时间，过期来源不得覆盖已确认新版本（f34）；回填时间不得当作发生时间（f13）。
4. 字段口径：关键字段白名单=商品编码、数量、单位、金额、币种、版本；缺失值与未确认值必须区分标记（f31）；质检发现问题记录保留原行（f33）。
5. 版本判定：以"版本有效期+确认状态"双条件判定，作废记录保留原因，禁止按文件名猜最新版本（f24）。
6. 审计留痕：查询、建议、确认全链路记录"谁查过、用哪个版本、提什么建议、谁确认"，不得只留最终摘要（f45）；留存原始版本、修订原因与确认人（f43）。
7. 数据性质标注：全部样本数据标注"合成演练"，系统输出页眉固定显示"合成演练 · 不代表真实授权、业务执行或客户验收"；保留期限与删除审批未定口径前不实现物理删除（f43）。

【代码规范】

- 每个函数写中文 docstring，说明入参、出参、失败时的行为。
- 关键业务逻辑（安全审查、权限校验、人工确认）必须写中文行内注释，说明为什么这么卡。
- 配置文件统一放 config.yaml，禁止把密钥、模型地址写死在代码里。
- 所有对外接口返回统一结构：{"ok": bool, "data": ..., "error": {"code": str, "msg": str}}

【交付要求】  
每个阶段结束时，给我：① 变更文件清单；② 启动与自测命令；③ 一段能直接跑通的验证脚本；④ 你认为这一阶段最可能出问题的地方。不要给我解释性长文，我要能跑的代码。每行代码必须添加注释。

【分阶段计划（建议，可调整）】

- 阶段 1：项目骨架——config.yaml、统一响应结构、SQLite 建表（单证/版本/交接/审计/人工队列五类表）、只读数据导入器。
- 阶段 2：核心比对——字段白名单校验、缺失/未确认区分、版本双条件判定、缺项清单+来源定位生成。
- 阶段 3：流程与红线——人工队列流转、业务负责人确认接口、双时间戳、过期来源拦截。
- 阶段 4：审计与验收——全链路审计留痕、50 票样本验收脚本（预设差异全部定位到原单据字段）、Jinja2 缺项清单页面。
